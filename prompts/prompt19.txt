## Prompt 19 — Period Reviews & Layered Mentor Memory

### Vision
Daily mentor coaching stays **light and event-driven** (Prompt 18).
Deeper history questions — “how was my week?”, `/7`, “סיכום חודשי” — are answered by
**on-demand full app snapshots** injected into mentor chat, not by sending full logs on
every normal chat turn.

**Phase 1 (shipped):** chat-triggered full snapshot → Gemini analyzes in one reply.
**Phase 2 (deferred):** daily rollups + cached weekly/monthly artifacts to cut repeat
token/API cost (see bottom of this file).

```
┌─────────────────────────────────────────────────────────────┐
│  Token layers (as built)                                    │
├─────────────────────────────────────────────────────────────┤
│  Every chat/coach turn │ Today stats + meal log + rules     │
│  Every chat/coach turn │ TODAY WORKOUTS (+ HR/session)      │
│  Every chat/coach turn │ YESTERDAY WORKOUTS (+ HR/session)  │
│  Every chat/coach turn │ Yesterday chat one-liner (P18)     │
│  On demand only        │ PERIOD REVIEW full snapshot block  │
│                        │ (/1 /7 /30 /100 or summary chips)  │
└─────────────────────────────────────────────────────────────┘
```

Prompt23 adds a **data-awareness layer**: each chat turn tells the mentor its current data
scope (today/yesterday/CGM window) and that the user can expose deeper history with `/N`.

### Prerequisites (Prompt 18 — already built)
- `CoachService.ts` — `triggerCoachReview`, `refreshCoachReview`, frequency gate
- `ChatScreen.tsx` — per-mentor tabs, collapsible coach panel with voice cards,
  bottom toolbar (scroll / clear tab / HTML export / send), FAQ question bar, gated ↻ refresh
- `GeminiService.ts` — `chatWithMentor`, `generateCoachMessage` (+ `mentorLines`), `summariseChatDay`
- `TargetService.ts` — coach message, per-mentor chat history, quick questions, language, mentor gender
- `mentorChatExport.ts` — HTML export (tasks + all mentor chat sections)
- Event triggers: meal, weigh-in, workout, day-close

## PART A — Period review triggers (ChatScreen + ReviewService.ts)

No separate dashboard button. Discoverability via **quick-question chips** and
**slash commands** in chat.

### Slash commands (power users)

| Input | Window |
|-------|--------|
| `/1`, `/yesterday` | Yesterday |
| `/7` | Last 7 days |
| `/30` | Last 30 days |
| `/N` | Last N days, N ≤ `MAX_REVIEW_DAYS` (128) |

### Natural language (chips + free text)

| Hebrew | English equivalents | Days |
|--------|---------------------|------|
| סיכום אתמול | Yesterday summary, review yesterday | 1 |
| סיכום שבועי | Weekly summary, review my week | 7 |
| סיכום חודשי | Monthly summary, review my month | 30 |

Detection: `detectPeriodReviewQuery(text)` → `PeriodReviewRequest`:
```ts
export type PeriodReviewRequest =
  | { mode: 'yesterday' }
  | { mode: 'days'; days: number };

export const MAX_REVIEW_DAYS = 128;
```

On Send, `chatWithMentor(activeMentor, ...)` calls `buildPeriodReviewBlock(request, macroTarget)` and
appends the block to the system prompt with `PERIOD_REVIEW_CHAT_INSTRUCTION`.
Period reviews work from **any mentor tab** — same snapshot, reply in that mentor's voice.

**UX:** chip tap fills input; user taps **Send** (same as Prompt 18 — no accidental sends).
Long reviews (`/30`, `/100`) may take several seconds while Withings intraday data loads.

## PART B — Full snapshot content (`buildPeriodReviewBlock`)

When a period review is triggered, assemble **everything the app knows** for the window.
This is intentionally richer than rollup-only summaries — mentors cite real numbers.

### Data sources (fetched in parallel where possible)

| Source | API / service | Content |
|--------|---------------|---------|
| Food | `FoodLogService.getDailyMacros` + `buildMealsAiContext` | **Full meal item log** every day in window |
| Workouts | `WithingsApiService.fetchWorkoutsHistory` | Sessions with time, duration, active kcal |
| Body trend | `fetchBodyCompositionTrend7d` | wt, fat, muscle, visceral, BMR, activity kcal/day |
| Energy | computed locally | eaten vs burn (BMR + passive + workouts), deficit/surplus |
| Heart rate | `fetchHeartRateHistory(N)` + Health Connect | 24/7 daily avg/min/max + **per-workout HR** |
| CGM | `healthMetricsCache` + CareSens CSV + HC | Filtered glucose, meal correlation, period stats |
| Trends | `metabolicTrend7d` helpers | Period weight/BIA/visceral/BMR deltas |
| Macros | local | Adherence vs `DailyMacroTarget` |

### Per-workout HR correlation (every coach turn + period reviews)

`buildYesterdayWorkoutRollup()` and period blocks include, for each workout:
```
Walk 08:15–09:02 (47 min, 210 kcal active)
    HR during session: avg 118 max 142 bpm (38 readings) | resting baseline ~68 bpm | +10 min recovery avg 82 bpm
```

HR points filtered to `[startMs, endMs]`; resting baseline = day HR excluding all workout windows;
recovery = avg bpm in +5–15 min after session end.

### Heart rate fetch notes

- Withings `getintradayactivity`: one API call per calendar day; parallelized (6 concurrent).
- Health Connect (`SamsungHealthService.fetchRecentMetrics`) merged for the review window.
- Full HR detail for entire period (no artificial day cap).

### CGM glucose (CareSens / Health Connect) — shipped

Mentors (Nutritionist 🥗, Doctor 🩺) must cite **avg / min / max** and range percentages — not vague summaries.

**Pipeline** (`cgmWarmupFilter.ts`, `cgmStatisticalFilter.ts`, `cgmRangeStats.ts`, `mealGlucoseAnalysis.ts`):

1. **Multi-session warm-up** — first 24h after each **CareSens CSV serial** session only; **24h+ gaps** (e.g. CSV export end → HC live stream) do **not** trigger warm-up (would hide live HC after import).
2. **Statistical filter** — if ≤5% of CGM days have daily min &lt;54 mg/dL (and ≤3 days), exclude those whole days as likely sensor error (e.g. isolated Apr 7 @ 40 mg/dL).
3. **Range stats for mentors** — % readings below 70, 70–100, above 100 mg/dL; **low-day count** (days with daily min &lt;70); compression-low guidance when relevant.

Period block includes `GLUCOSE & FOOD IMPACT (period)` with period avg/min/max, range %, low-day count, meal spike correlation when meals logged.

Everyday coach/chat: `buildGlucoseMentorContext()` — today/recent CGM + meal glucose when data present.

### Period block structure (abbreviated)

```
=== PERIOD REVIEW: LAST 7 DAYS (YYYY-MM-DD → YYYY-MM-DD) ===
Macro targets: …
TREND ANALYSIS (period): weight Δ, BIA fat/muscle, visceral, BMR avg
MACRO ADHERENCE: …
GLUCOSE & FOOD IMPACT (period): avg/min/max, range %, low days, meal spikes
DAILY DETAIL (newest last):
--- YYYY-MM-DD ---
BODY: wt … | fat … | muscle … | visceral … | BMR … | Withings activity …
ENERGY: eaten … | burn … | balance …
HEART RATE (24/7): avg … | min … | max … | N readings
FOOD & MEALS: (full item detail)
MEAL GLUCOSE / CGM day stats (when samples in window)
WORKOUTS (+ HR during each session): …
=== END PERIOD REVIEW ===
```

### Everyday chat (no period review)

Compact only:
- `TODAY WORKOUTS` + `YESTERDAY WORKOUTS` with HR-during-session lines (3-day HR fetch; single Withings fetch via `buildChatWorkoutRollups()`)
- Today meal log, coach context, yesterday chat one-liner (Prompt 18)

## PART C — GeminiService wiring

```ts
// ReviewService.ts
export async function buildPeriodReviewBlock(
  request: PeriodReviewRequest,
  macroTarget?: DailyMacroTarget | null,
): Promise<string>;

export async function buildChatWorkoutRollups(): Promise<{ today: string; yesterday: string }>;
export async function buildYesterdayWorkoutRollup(): Promise<string>;
export async function buildTodayWorkoutRollup(): Promise<string>;

export const PERIOD_REVIEW_CHAT_INSTRUCTION = '…'; // full snapshot + HR vs workout guidance
```

`chatWithMentor(mentor, ...)`:
1. `detectPeriodReviewQuery(message)` on user text
2. If match → `buildPeriodReviewBlock` → append to system prompt
3. User turn augmented: “Use the PERIOD REVIEW block…”

Coach prompt additions:
- Workout events: comment on HR during session vs resting baseline when present
- Period reviews: each active mentor — what went well, improve, 2–4 concrete steps
