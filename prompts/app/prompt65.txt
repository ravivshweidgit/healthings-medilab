**Status: Phase A in progress (2026-07-10)** — EAS config, HC platform stubs, iOS source_config guards; TestFlight build pending EAS credentials.  
**Trigger:** Apple Developer Program enrolled — TestFlight unblocked.  
**Builds on:** `done/prompt55.txt` · `done/prompt58.txt` · `prompt47.txt` (Play pattern) · **`prompt56.txt`** (full HealthKit path — **deferred to Phase 2 here**)

---

### Problem

Android alpha is on Play Internal (1.2.1). iPhone testers cannot install. The app UI is React Native; **native health layer is Android-only today** (Health Connect, `react-native-health-connect`).

**Product question (2026-07-10):** Should iOS v1 avoid Apple **HealthKit** and ship **Withings cloud only** (same OAuth + API path as Android)?

---

### Recommendation (best practice)

**Ship TestFlight in two layers — do not block iOS on HealthKit.**

| Phase | Scope | Goal |
|-------|--------|------|
| **65 Phase 1 (this prompt)** | Withings cloud + manual body + food/coach/clinic + CSV CGM import | **Fast, low-risk TestFlight** for Withings-scale/watch iPhone users |
| **56 Phase 2 (later)** | HealthKit glucose + steps when a real iPhone CGM tester needs live chart | Parity for CareSens/Libre → Apple Health users |

**Why not HealthKit in v1:** entitlements, privacy nutrition labels, native module + Expo dev client, permission UX, and CGM vendor quirks — all **orthogonal** to proving the coaching loop on iPhone.

**Why not Withings-only forever:** on iPhone there is **no Health Connect**. Users without a Withings watch get **no live activity/steps** until HealthKit or manual-only. **CGM-on-iPhone** almost always flows through **Apple Health**, not Withings API.

---

### Challenge the “Withings-only” thesis

| Claim | Verdict |
|-------|---------|
| “Withings doesn’t depend on Apple Health Connect” | **True for data path** — app uses **Withings OAuth + cloud API** (`syncWithingsApiIntoStore`), same on iOS and Android. No HC on iOS required for scale/watch/body/workouts/HR. |
| “So we can skip HealthKit entirely” | **True for v1 alpha** if testers are **Withings scale ± watch** and CGM is optional (CSV import OK). |
| “Garmin users need iOS” | **No** — Garmin path is **Android Health Connect** (`prompt64`). Colleague testing stays Android. |
| “iOS = same feature set as Android” | **False without HealthKit** — Android CGM via HC, Android activity via HC/Garmin, Android steps via HC. iOS v1 = **intentional subset**. |
| “Withings watch writes to Apple Health anyway” | **Irrelevant if cloud is SSOT** — do **not** read the same metrics from HealthKit *and* Withings (double-count risk). Pick one source per metric in `source_config`. |
| “Faster to market” | **Yes** — reuse `MetricsPersistenceService`, `WithingsApiService`, `useWithingsData`, clinic export unchanged. |

**Bottom line:** Withings-first is the **correct v1 wedge** for your current alpha cohort; document **explicit gaps** for iPhone CGM and non-Withings watch users.

---

### Persistence parity (required — project rule)

**Rule:** `.cursor/rules/persistence-parity.mdc` (`alwaysApply: true`)

iOS v1 must **not** introduce platform-specific user-data keys or parallel metric stores. Reasons:

1. **Clinic integrity** — portal parses one snapshot shape (`healthings:metricsStore`, food logs, rules, …); Android/iPhone blobs must match.
2. **Free OS migration** — local + cloud backup JSON is platform-agnostic; user restores on the other OS with no conversion.

**iOS implementation checklist:**

- [ ] All sync goes through `syncMetricsStore()` → same `metricsStore` schema as Android
- [ ] Backup import runs `coalesceMetricsStores()` + `source_config` platform normalize (HC enums → safe iOS defaults)
- [ ] No new `Platform.OS`-specific AsyncStorage keys for user state
- [ ] `ShareExportService` / `LocalBackupService` stay aligned on exclusions + canonical metrics injection

Adapters (Withings cloud, future HealthKit) differ; **persisted keys and JSON shapes do not**.

### Platform defaults (iOS bootstrap)

On first `loadSourceConfig()` when `Platform.OS === 'ios'` and no saved config:

```jsonc
{
  "version": 1,
  "glucose": "none",           // until prompt56 — CSV import bypasses source_config
  "activity": "withings",      // if user says watch Y; else "none" (not health-connect)
  "bodyComposition": "withings" | "manual",
  "bmr": "withings" | "manual" | "ai-estimate",
  "heartRate": "withings" | "none"
}
```

**Hard rule:** never set `health-connect` or `samsung-steps` on iOS — those types are Android-only. `sourceConfigFromToggles` must accept `platform: 'ios' | 'android'`.

**Dashboard guards:**

- Hide `HealthConnectStepsGuide`, HC permission banners, “Connect Health Connect” CTAs.
- Hide glucose strip live-sync UI unless `glucose === 'healthkit'` (future) or show CSV-import path only.
- `syncHealthConnectIntoStore()` no-op on iOS (already gated by activity source — add `Platform.OS` guard as belt-and-suspenders).

### Architecture (unchanged store, fewer adapters)

```
Shared UI (screens, wizard, clinic)
        │
        ▼
source_config + Platform.OS
        │
   ┌────┴────┐
   ▼         ▼
Android     iOS v1
HC +        Withings API + manual + CSV CGM
Withings    (no HealthKitService yet)
   │         │
   └────┬────┘
        ▼
healthings:metricsStore  ← same SSOT, clinic export, mentors
```

**Do not fork** `WithingsPersistenceService` / dashboard hooks — iOS reads the same `useWithingsData()` + `syncMetricsStore()` (Withings branch only).
