## Architecture vision — persistence-first, sync-as-adapter

This prompt is the guiding doc for both backup **and** future data-source integrations.
The backup feature is the first concrete expression of a deeper architectural principle.

### Principle 1 — Local persistence is the single source of truth
- Everything the user owns lives in **local storage on the phone** (AsyncStorage +
  SecureStore). This is the durable layer.
- The UI reads **only** from persistence — never directly from an external API.
- Backup = a snapshot of this one layer. Restore = merge back into it.

### Principle 2 — Sync feeds persistence; it never owns it
- External sources (Withings, CareSens/xDrip+ → Health Connect, Samsung Health, Libre,
  Tanita, …) are **upstream feeders**. Their only job is **fetch → normalize → merge into
  the local store**.
- Merge is **additive and idempotent**: new points fill gaps, existing points stay. A sync
  never wipes or "owns" the truth.
- Because the truth is local, **sync stays dumb and cheap** — pull N days, merge, done. No
  reconciliation, no "which side wins" state machine, no heavy sync engine.

### Principle 3 — Provider-agnostic adapters (the contract)
The persistence layer defines a **stable, normalized shape per metric**. Every device or
service is just a swappable **adapter** that maps its data into that shape. The rest of the
app never knows or cares where a data point came from.

Canonical local stores (the contract):
- **Glucose** → `healthings:lastMetrics.glucose` + `cgmSessionStarts`
- **Activity / calories burned** → day-keyed local store
- **Body composition** (weight / fat / muscle / BMR) → local store
- **Heart rate** → local store

Interchangeable adapters (each only does fetch → normalize → merge):
| Source | Feeds | Notes |
|---|---|---|
| CareSens → xDrip+ → Health Connect | Glucose | current |
| **Libre** (LibreLinkUp / HC) | Glucose | drop-in, same merge |
| Withings | Body comp, HR, activity calories | current |
| **Samsung Health** (steps) | Activity → calories (derived) | steps × formula → kcal |
| **Tanita** (if/when API) | Body composition | drop-in |

Rules that keep this clean:
1. **One normalized shape per metric** — merge logic written once *per metric*, not per provider.
2. **Idempotent + source-tagged merge** — dedupe by timestamp/day; optionally stamp each point
   with its `source` so conflicts resolve (e.g. prefer Withings calories over Samsung-derived)
   without rewriting merge.
3. **Adapters are pluggable** — adding Libre / Tanita = write one adapter + register it. Zero
   changes to UI, persistence, or other adapters.
4. **Derived metrics are just another adapter** — Samsung steps → kcal is a transform that
   merges into the *same* activity store; the store doesn't know it was derived.

### Trigger (user request 2026-06-10)
All app data lives **only** on the phone (AsyncStorage + SecureStore). If the phone is
lost or the app is reinstalled, everything is gone: food log, manual burn edits, profile,
targets, mentors/rules, chat history, and the CGM (glucose) cache.

Cloud sync is **explicitly off the table** — health data in the cloud means HIPAA / GDPR /
medical-device regulatory burden (BAAs, residency, breach liability). The user wants a
**100% local, user-controlled** backup instead:

> "JSON yes — export creates a file with CGM and all Withings data, all local data exported.
>  You can export/import this data."

Design model:
- **Export** → app writes a single `healthings-backup_YYYY-MM-DD.json` to a folder the user
  picks (Downloads, Drive, email-to-self). The user owns the file; nothing leaves the device
  unless they move it.
- **Import** → user picks that file back; app merges/restores into local storage.
- No servers, no accounts, no PII in transit. Regulatory surface ≈ zero because we never hold
  the data.

This extends the existing `exportFoodLog` / `importFoodLog` pattern (food only) to **all**
local app data.

## Backup file format (versioned envelope)

```jsonc
{
  "version": 1,
  "app": "healthings-medilab",
  "exportedAt": "2026-06-10T19:00:00.000Z",
  "asyncStorage": { "<key>": "<raw string value>", ... },  // includes healthings:withingsStore, healthings:lastMetrics, food_log_*, etc.
  "withingsTokens": { "accessToken": "...", "refreshToken": "...", ... } | null
}
```

- `withingsSnapshot` in envelope is **optional** — only if we need a legacy fallback; v1 can
  rely on `healthings:withingsStore` inside `asyncStorage`.

- `asyncStorage` is captured generically via `AsyncStorage.getAllKeys()` minus the exclude
  set — so future keys are backed up automatically without code changes.
- Validate on import: `version === 1` and `app === 'healthings-medilab'`; else throw.

## Implementation plan

### New service: `app/src/services/LocalBackupService.ts`
- `buildLocalBackupPayload(): Promise<LocalBackupPayload>`
  - `AsyncStorage.getAllKeys()` → filter exclude set + `healthings:withingsBackup` → read each.
  - `loadWithingsTokens()` for `withingsTokens`.
  - When Withings linked, pull live snapshot (`fetchWeightMetrics`, `fetchBodyCompositionTrend7d`,
    `fetchHeartRateHistory(128)`, `fetchWorkoutsHistory(128)`), each guarded with `.catch(() => null)`;
    fall back to cached `healthings:withingsBackup` if the pull fails / not linked.
- `exportLocalBackup(): Promise<void>`
  - SAF directory picker (same as `exportFoodLog`) → write `healthings-backup_{today}.json` pretty-printed.
- `importLocalBackup(): Promise<LocalBackupImportResult>`
  - DocumentPicker (`application/json`) → read → validate envelope.
  - **Merge** strategy (never blind-wipe):
    - `food_log_*` → merge by meal `id` (reuse the `importFoodLog` rule).
    - `chat_history_*` → merge by `(sentAt|role|text)` dedupe.
    - `healthings:lastMetrics` → merge glucose/steps/HR by epoch ms (`mergeGlucoseTimePoints`)
      + `mergeCgmSessionStarts`.
    - all other keys → restore (overwrite) from backup.
  - Restore Withings tokens via `saveWithingsTokens` (Tier 3).
  - Store `withingsSnapshot` under `healthings:withingsBackup`.
  - Return counts: `keysRestored`, `mealsAdded`, `glucosePointsMerged`, `withingsSnapshotRestored`, `tokensRestored`.

### UI: Dashboard "My Profile" group (`DashboardScreen.tsx`)
- Add **Export all data** + **Import all data** buttons (new row in the profile/targets group card,
  or a small "Backup" subsection). Busy state + `ActivityIndicator`.
- On export success → `Alert` "Backup saved to the folder you picked."
- On import success → reload all local data (`refetch`, `loadBodyScan`, `loadTrend`, `loadHeartRate`,
  `loadWorkouts`, `loadTodayFood`), then `Alert` with the per-section counts.
- Cancel (user dismissed picker) → silent no-op.

### Optional follow-up (not required for v1)
- Dashboard reads `healthings:withingsBackup` as a fallback so restored Withings metrics render
  before the user re-links.
- Encrypt-at-rest option for the file if tokens are included (or simply exclude tokens by default
  and offer "include Withings login" as an explicit checkbox).

## Constraints / decisions
- **Local only. No AWS / cloud. No accounts.** (`AwsDataService` stays unused for this.)
- Single JSON file, versioned, merge-on-import (idempotent — re-importing adds nothing new).
- Generic key capture so new AsyncStorage keys are covered without touching the backup code.
- Withings tokens are sensitive: default include (so restore re-links), but document the risk;
  a future toggle can exclude them.
