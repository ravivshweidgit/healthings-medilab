## Why v1 was pulled (2026-08-25) — read before rebuilding

**One** camera meal was enough to make the whole dashboard feel slow. Neither cause was the
JPEG, and the sections below were rewritten because they prescribed both:

1. **Disk I/O on the render path.** `resolveMealPhotoIds` in `MetabolicChart.tsx` ran one
   `getInfoAsync` per camera meal to decide the 📷 mark, from a `useEffect` keyed on
   `foodEntries` — a fresh array every dashboard render — then `setState`, forcing another
   render. Cost scaled with *re-render frequency*, not photo count. `photoId` already was the
   answer.
2. **File bytes inside the gzipped snapshot.** `injectMealPhotosSidecar` base64'd thumbs into
   the `asyncStorage` map, so every `buildClinicExport` re-ran `JSON.stringify` + `pako.deflate`
   over a year of unrelated data with the photo attached. That export is **not** Share-only: it
   runs on launch and foreground (`pushSnapshotForWebView`), on clinic Refresh
   (`fulfillPendingClinicSyncRequests`), and on cloud backup.

Both were mitigated first (TTL file-index cache, 15s debounced purge, deferred launch purge,
`setTimeout(0)` yields) and still felt wrong — the mitigations were the signal. See
`render-path-reads-memory.mdc`.

Camera → Gemini analysis was never removed and still works.

## Rebuild contract (supersedes "Design rules" and section C below)

Four cuts, all four required. Any one alone is insufficient:

| Cut | Rule |
|---|---|
| **Trigger** | Photos move only on an explicit Share tap. Auto sync / web-view push / cloud backup stay photo-free **forever**. |
| **Transport** | File bytes never join the snapshot JSON. Separate binary endpoint. Snapshot carries `photoId` strings only (~64 B/meal). |
| **Representation** | Bytes never enter JS: `FileSystem.uploadAsync(url, fileUri, { uploadType: BINARY_CONTENT })`. No base64 anywhere — not on disk, not in AsyncStorage, not in a body. |
| **Repetition** | `photoId` = a **stable unique id per file**, so `POST /v1/meal-photos/missing` with the id list returns only what the server lacks. Second Share uploads nothing; retries idempotent. |

**How to get that id — do not reach for sha256.** There is no way to SHA-256 a file on this
stack without pulling its bytes into JS (`expo-crypto` hashes strings only, and is not
installed), which is the exact bug this batch exists to avoid. Two acceptable options:

- **Native md5** — `FileSystem.getInfoAsync(uri, { md5: true })` (legacy) or `File.md5` (new
  API). Computed natively, no bytes in JS. Content-addressed, so identical plates dedupe free.
  MD5 is fine here: the id is a storage key, not a security boundary — the server authorizes by
  share, never by id secrecy.
- **Random UUID** at capture. Simpler, no hash step, loses dedupe. The upload-once property
  only needs *stable and unique*, not content-derived.

Pick md5 unless it measurably slows capture. Either way the id is computed **once, at capture**,
and never recomputed — never on a render path.

Structural guard: put upload in its own module that `ShareExportService` **does not import**.
No gzip on JPEG (already compressed). Existing sync/cloud caps stay as they are — if a rebuild
wants them raised, bytes got back into the JSON.

Ship in three separately-verifiable phases; v1 shipped all of it at once, which is why one
photo was a mystery:

- **Phase 0 — protect the baseline.** Push / merge `perf/dash-expand-no-meal-thumbs` first.
  It is the only copy of the expand fixes and the reference the Phase 1 gate compares against.
- **Phase 1 — local only.** Capture, store, `photoId`, mark, meal-card display, purge. Zero
  server, zero export change. Take one photo, exercise every expand. Any change in feel = stop.
  Only new dependency in the whole batch: `expo-image-manipulator` (removed in the rollback).
- **Phase 2 — upload on tap.** Hash ids, missing-check, native upload. Everything except the
  Share button must feel identical.
- **Phase 3 — clinic lightbox** (be-53).

## Problem

People log meals with the app camera. Gemini sees the plate, then the JPEG is thrown away.
The clinic snapshot has kcal, items, and `source: camera-ai`. The orange triangle (e.g. 579)
has nothing to open. Clinicians ask “what was that plate?” about **recent** meals, especially
new users. Full-res originals would fill the phone; tiling photos on the 24H strip would
fight glucose / HR / walks.

## Design (owner, 2026-08-22)

- **One compressed thumb per camera meal** (~100 KB). Five camera meals ≈ **0.5 MB/day**.
  30 days ≈ **15 MB** high end (every meal a photo, every day). Text-only meals: no file.
- **Keep files 30 calendar days** on the phone, then delete. Meal **numbers stay forever**
  (triangle, kcal, items). Missing file = no camera mark, not a broken meal.
- **Share sends whatever thumbs still exist** that day (same consent as the rest of the
  snapshot). Local + cloud backup include the same files so a new phone still has the window.
- **UI:** do not paint photos on the chart. Tiny camera mark on the triangle / meal chip
  when a thumb exists. Tap triangle **or** chip → existing meal card with the plate on top.
- **One image per meal** (the plate used for the saved estimate — usually the before shot).
  After-meal leftover photos are not a second stored file in v1.

## Design rules

- Photos leave the phone **only on an explicit Share tap**, as a binary upload. Never inside
  the snapshot, never on auto sync / web-view push / opportunistic cloud backup.
- **Persistence parity:** `photoId` on `FoodEntry` is the canonical pointer (native md5 or
  UUID — see Rebuild contract). Files live under
  `documentDirectory/healthings-meal-photos/{photoId}.jpg` — **no** `Platform.OS` in the path
  or AsyncStorage key. Same shape Android ↔ iOS.
- **No base64 anywhere** — not in `food_log_*` JSON, not in AsyncStorage, not in a request
  body, not as a `data:` URI. Raw JPEG in a file is the only at-rest form.
- **No I/O to decide the mark.** 📷 comes from `Boolean(entry.photoId)` on data already in
  memory. A mark pointing at a purged file is cosmetic — handle it with `onError` on the
  `<Image>` in the open card (`render-path-reads-memory.mdc`).
- **Do not** parse meal names to decide what to show (`ai-judgment-not-regex`).
- **Do not** dump thumbs into mentor chat or clinic Gemini context. Human lightbox only.
- Existing caps stay: clinic upload **15 MB gzipped**, cloud backup **25 MB**. The snapshot
  grows by one id string per camera meal, so neither is under pressure.

## What ships (app)

### A. Save thumb on camera save

- After a new/edited meal is saved from a photo, write one JPEG: longest edge ~720–800 px,
  quality such that typical plates land **~80–120 KB** (owner math: 100 KB). This resize is
  the only compression in the design.
- Set `FoodEntry.photoId` from the native md5 (or a UUID). Editing a meal (time,
  items) must carry `photoId` forward untouched — v1 lost the plate on a time edit because the
  entry moved day-key and was re-saved without it.
- Replacing the photo writes a new file and repoints `photoId`; the orphan goes on the next
  purge. Deleting the meal deletes the file.
- Text-only / manual meals: leave `photoId` unset.

### B. 30-day purge

- On launch and after meal save: delete files whose meal timestamp is older than 30
  calendar days (local timezone, same day-key rules as `food_log_*`). Clear `photoId` on
  those entries so the JSON does not point at a missing file.
- Cap is **days**, not a 15 MB quota. Quiet weeks just use less disk.

### C. Share upload (own module, not the export path)

- New `MealPhotoUpload.ts` — the only module allowed to touch photo bytes. `ShareExportService`
  must **not** import it; the tap handler calls both.
- On Share tap, after the snapshot upload succeeds: collect `photoId`s of meals inside the
  window, `POST /v1/meal-photos/missing` with the id list, then `uploadAsync` each returned id
  with `uploadType: BINARY_CONTENT`. Queue failures for the next Share — never retry in a loop.
- Photo upload failure must not fail the Share. Numbers are the product; the plate is a bonus.

**Backup — decided (owner, 2026-08-25): photos do not travel in backups.** Local and cloud
backup carry meal numbers as they do today and no plate bytes, ever. A restored phone shows
every meal, kcal, and item with no camera mark — the same state as a meal whose file aged past
30 days, which the design already treats as normal ("missing file = no camera mark, not a
broken meal"). Photos are cosmetic and 30-day; keeping backups base64-free is worth more.

This is why `LocalBackupService.ts` and `CloudBackupService.ts` appear in *unchanged on
purpose* below. A future owner who wants plates to survive a phone switch should add a
zip/folder beside the JSON — a new batch, never an inline map.

### D. Phone chart + Food Log (light)

- Metabolic chart: camera glyph on the orange triangle when `Boolean(entry.photoId)` — a pure
  expression, no effect, no state, **no disk check**. Tap opens the meal (existing Food Log
  edit/view) with the thumb — **not** a second photo-only overlay unless the current meal sheet
  cannot show an image.
- Food Log chips: same camera hint, same pure check.
- The meal card is the **only** place an `<Image>` mounts, with a fixed width/height so there
  is no re-layout, and `source={{ uri: 'file://…' }}` so decode stays on the native thread.
- Dense 6H/24H: skip the glyph before skipping the kcal label if the lane is crowded;
  never overlay a thumbnail on the plot.

## Out of scope (explicit)

- Full-resolution originals, photo gallery, or a second after-meal file
- Clinic AI / phone coach reading the JPEG
- Photos older than 30 days (even if the clinic asks later — they needed a Share while
  the file still existed)
- Changing meal-item macros from the photo in the portal (view only)
- Pixel-perfect chart chrome — owner on device

## Phone checklist

**Phase 1 gate — one photo, then stop and feel it.** This is the check v1 never ran.

- [ ] Camera meal → file on disk ~100 KB; `photoId` = sha; triangle shows camera mark
- [ ] With exactly **one** photo saved: expand/collapse Mentors, Glucose, Food Log, Activity,
      Your setup — indistinguishable from `perf/dash-expand-no-meal-thumbs`. Any drag = stop.
- [ ] Edit that meal's **time** → plate survives; edit items → plate survives
- [ ] Text meal → no file, no mark
- [ ] Tap triangle / chip → plate on the meal card, then items / kcal as today
- [ ] Meal from 31+ days ago: numbers remain, file gone; stale mark opens a card that degrades
      quietly via `onError` (no crash, no spinner)
- [ ] Delete meal → file gone
- [ ] 24H strip still readable (no photo tiles under Walk / kcal)
- [ ] he/ar: meal names still `dir=auto`; no extra Latin in running copy

**Phase 2 gate**

- [ ] Share with photos → clinic (be-53) can open them; Share with 0 photos still works
- [ ] **Second** Share uploads nothing (missing-check returns empty)
- [ ] Airplane mode mid-Share → snapshot result unaffected, photos queue for next tap
- [ ] Launch / foreground / clinic Refresh with photos on disk → no photo traffic at all
- [ ] Backup export/import on a second install: every meal number intact, **no plates, no
      camera marks, no base64 in the file** (decision (a), section C)
