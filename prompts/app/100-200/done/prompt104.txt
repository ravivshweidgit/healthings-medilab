## Calorie merge

Manual/favorite session kcal **adds** to wearable/hybrid activity for that day (Food Log activity line + burned). Adjust activity kcal remains an override on top. Wearable sessions stay in `metricsStore` (display-only chips); not double-counted from Activity Log storage.

## Problem

Activity kcal today is mostly wearable sync + a blunt **Adjust activity kcal** correction. Users who do YouTube / bodyweight / gym sessions (no watch, or watch undercounts) have no Food-Log-like place to log sessions, reuse favorites, or attach a reference video/photo.

## Product rules (agreed)

1. **UI twin of Food Log** — dashboard strip under Food Log (“ACTIVITY LOG”): same day chrome (prev/next date), day total, horizontal chips / rows, collapse/expand.
2. **Quantity = minutes (required).** No grams. No structured sets×reps in v1.
3. **Optional free-text note / instruction** — e.g. “3×12 pull-ups, last to failure” or “did the video twice.” Gemini may use note (+ optional photo) for kcal/intensity judgment; do not parse sets with regex.
4. **User favorites library** — user-created list (not a built-in catalog):
   - name
   - default minutes
   - optional default note
   - optional YouTube URL (e.g. https://youtu.be/R5uLtIAfd9s)
   - optional reference image
5. **Log entry sources**
   - **Manual / favorite** — user picks favorite or types name + minutes (+ note / photo / YouTube).
   - **Wearable** — existing `metricsStore` / HC / Withings `WorkoutSession` rows appear in the day list with a source badge; user can edit label/note lightly; do not invent a second workout store for vendor data.
6. **Day activity total** — sum of logged session kcal for that day feeds ENERGY BALANCE / Food Log burn line. Prefer wearable kcal when present; else Gemini estimate from name + minutes + note/photo; else a simple duration×intensity fallback.
7. **Adjust activity kcal** — keep as rare **override** on top of the log (not the primary UX).
8. **Language** — strip chrome + modals follow `appLocale` (same pattern as Food Log copy). Always-English glossary: kcal, BMR, YouTube, CGM, etc.
9. **Persistence parity** — canonical AsyncStorage keys (shared Android/iOS). No `Platform.OS` in key names.
10. **Backup defensive rule (do not backup less than the phone DB)**  
    Local / cloud backup already dumps **`getAllKeys()` minus a small ephemeral exclude set** (`LocalBackupService` / `ShareExportService` `EXCLUDED_ASYNC_KEYS`). Keep that model:
    - **Never** switch to an allowlist of keys to export — that silently drops new stores.
    - Activity favorites + day entries **must not** be added to either exclusion list.
    - When adding a key, default = **included**. Only put debug / billing / ephemeral keys on the exclude lists; update **both** lists together if you exclude anything.
    - If favorite/session images live as file URIs outside AsyncStorage, either store payload bytes (or a durable key) inside AS so backup carries them, or explicitly copy those files into the backup payload — **do not** leave dangling paths that restore empty on another phone.

11. **Activity-specific defensive check (required — not covered by meal/HR alone)**  
    Meals and HR already block thin phones from wiping richer cloud copies (`backupFingerprint.ts` → `canOverwriteCloudBackup`: never overwrite with fewer `mealDays` / less HR). **Activity must get the same treatment**, as its own dimensions — do not assume meal/byteSize checks protect workouts/favorites.

    | Check | Behavior |
    |-------|----------|
    | **Fingerprint fields** | Add e.g. `activityDays` (day keys with ≥1 activity entry), `activityEntries` (total session count), `activityFavorites` (favorite count). Count from activity-log keys + favorites key in the payload. |
    | **Cloud overwrite** | In `canOverwriteCloudBackup`: refuse if phone `activityDays` / `activityFavorites` / `activityEntries` is **less** than cloud (same tone as meals: restore or force replace). Empty phone must not wipe a cloud that has activity history. |
    | **Export assert** | After `collectAsyncStorageExport`, compare device activity keys/counts vs payload; if the phone has favorites or day entries that are missing from the payload → **fail the export** (log + user-visible error), do not write a thin file. |
    | **Import merge** | Mirror food-day merge by entry `id` for activity day keys; refresh activity day index after import (like `refreshFoodDayIndex`). Favorites: merge by favorite `id` (union, never drop cloud-only or phone-only without force). |
    | **Clinic / account share** | Same keys ride the shared dump unless privacy policy excludes them; if excluded, document why — default is **include** (health behavior data). |

    Emptyish heuristic (`isEmptyish`) should treat “no meals and no glucose” **or** consider activity: a phone with only activity history is not empty for overwrite purposes if cloud also has activity — extend carefully so activity-only users are protected.

## Data sketch (v1)

```
ActivityFavorite {
  id, name, defaultMinutes, note?, youtubeUrl?, imageUri? (or stored blob key), createdAt
}

ActivityEntry {
  id, dayKey, timestamp,
  name, minutes, note?,
  youtubeUrl?,           // copy from favorite or paste
  imageUri?,             // optional camera/gallery + prompt like meal
  activityKcal,          // estimated or from wearable
  source: 'manual' | 'favorite' | 'withings' | 'health-connect' | 'healthkit',
  favoriteId?,           // if logged from favorite
  wearableStartMs?       // link to WorkoutSession when mirrored
}
```

Favorites key e.g. `healthings:activityFavorites`  
Day entries e.g. `healthings:activityLog` / per-day index parallel to `food_log_days` — exact names locked at implement time; document in this file when shipped.

## Implementation notes

- Mirror Food Log patterns: service + strip + modal; `appLocale` copy module.
- KeyboardAvoidingView on iOS for any TextInput modals (prompt103-era lesson: Adjust activity modal).
- Wearable merge: read `WorkoutSession` from existing loaders; write manual entries only to activity-log store; never fork `metricsStore` for manual rows.
- **AI kcal (high-end):** when a public YouTube URL is present, `estimateActivityKcalFromYoutube` sends `fileData.fileUri` (watch URL) so Gemini **watches** the workout (TV follow-along intent). Returns `durationMinutes` from the film length and sets the minutes field (e.g. 12:07 → 12) + kcal for that duration — ignores stale UI defaults like 30. Optional `equipmentWeightKg` (dumbbell/bar load, not body weight) is stored on entries/favorites and passed into AI. Name-only stays text fallback. Private/unlisted links fail with a clear error.
- Android first: `app\build-APK.bat install` (`bi`); do not commit until Samsung phone-tested.
