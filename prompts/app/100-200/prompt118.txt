## Problem

The website has one plate collection (`lipid-protocol`) and the app links it from
**Log Meal** — hardcoded, for **every user**:

    onPress={() => void Linking.openURL(platesUrl(lang?.code ?? 'en'))}

So a pre-diabetes patient whose clinician wrote a glycemic order is shown a
cholesterol-period food diary. That is the bug this batch fixes.

The clinical decision already exists in the product: **the clinic writes rules**, and
Rules Save (or phone Analyze) runs Propose, which reads those rules as a clinician and
returns structured bounds + markers. Plates should ride that same decision — one more
field on a call we already pay for — not a second inference path.

## Design (owner, 2026-08-25)

**Rules drive the profile. Labs are the fallback, not the driver.**

Lab-only routing fails two real patients:

- **Treated:** statin patient with a clinician-written lipid order reads LDL `normal`,
  so `hasActionableMarker` is false — lab routing hides lipid plates from exactly the
  person whose clinician just ordered that diet.
- **Mismatched:** high LDL on paper while the actual order centers a renal protein cap —
  lab routing shows plates the clinician did not intend.

Precedence, highest first:

| # | Source | When |
|---|--------|------|
| 1 | Clinic explicit pin (`source: 'clinic_override'`) | Clinician overrides the AI read — **reserved, not v1** |
| 2 | **Propose `plate_collection`** from rules text | Whenever rules exist — the normal path |
| 3 | Labs `computeClinicalProfile().primary` → map | No rules yet; lab PDF imported |
| 4 | none | Hide the link (do **not** fall back to lipid) |

`ClinicMacroBoundsStore` already carries `rulesHash`, so the collection is versioned with
the rules that produced it: rules change → Propose reruns → collection refreshes. No
separate invalidation, no extra AI call.

## Design rules

- **Closed enum, validated server-side.** Propose returns a slug from a registry the
  server owns. Unknown / invented slug (`mediterranean-protocol`) → `null`, never a
  deep link to a 404. The registry is the single source of truth and must mirror what
  actually exists under `website/{lang}/plates/`.
- **Never string-match prose.** Do not route off `clinical_profile` — that field is
  deliberately free-form medical English (`"Lipid-primary + renal protein cap"`).
  Substring-matching it is the same failure mode as regexing the rules
  (`ai-judgment-not-regex`).
- **The app never reads rules text** to pick plates. It reads a slug.
- **No auto-navigation.** Never open the browser on Save / Accept. Show a link the user
  taps. Plates are illustrations, not a prescription.
- **Content gates routing.** Propose may only emit a slug whose pages exist in all
  `HELP_LOCALES`. Ship the website collection first, then widen the enum.
- Plates stay on the **website** (photos, disclaimers, 10 locales). The app only routes
  locale + slug, exactly like `helpUrl()`. Do not bundle plate content in RN.
- Plates are **Log Meal examples**, not validated meal plans. They do not have to satisfy
  the patient's macro bounds and must not claim to. Keep the existing
  "Not medical advice / confirm every meal in the app" disclaimer on every collection.

## What ships

### A. Server — collection registry + Propose field

- New `server/src/services/plateCollections.ts`: the enum, plus
  `normalizePlateCollection(raw): string | null` (trim, lowercase, membership check).
  v1 members: `lipid-protocol`, `glycemic-protocol` (add the second only when its pages
  are live).
- `proposeClinicMacroOrder()`: add `"plate_collection"` to the returned JSON shape and a
  short instruction block — choose the collection that matches the **primary intent of
  the order**, or `null` when no collection fits. List the allowed slugs verbatim in the
  prompt. Explicitly: `null` is correct and preferred over a near-miss.
- Parse it with `normalizePlateCollection` (same defensive style as `markers[]`).
- `MacroProposeResult` and `ProposedClinicMacros` gain `plateCollection?: string | null`.
- Persist it in the macros payload beside `rulesHash` / `reasoning`, and return it on
  `GET /v1/clinic/overlays` and `POST /v1/account/macros/rebuild`.
- **Built:** no route edits were needed — both endpoints return the whole
  `ClinicMacrosPayload` (overlays via `macrosPayloadFromUnknown`, rebuild via
  `buildMacrosWritePayload`), so the field rides through. `macrosPayloadFromUnknown` runs
  stored slugs back through `normalizePlateCollection`, so a slug retired from the registry
  stops resolving on read instead of being trusted forever.

### B. App — resolver + dynamic links

- `ClinicMacroBoundsStore` gains `plateCollection?: string`. Parse defensively; an
  unknown slug on an older/newer build resolves to none.
- New `app/src/logic/plateRouting.ts`:
  - `PROFILE_TO_COLLECTION: Partial<Record<ClinicalProfilePrimary, string>>` — the labs
    fallback map. `lipid → lipid-protocol`. Leave `weight` unmapped until a weight
    collection exists (unmapped = hide, not lipid).
  - `resolvePlateCollection({ store, labsPrimary }): string | null` implementing the
    precedence table.
- `FoodLogModal`: replace the hardcoded call with the resolved slug. **Hide the
  "Example plates" link entirely when the resolver returns none** — no lipid default.
- `MacroTargetStrip`: after **Accept**, a calm inline row — label from
  `foodLogUiCopy.examplePlates`, plus one short line that these are illustrations and
  every meal is confirmed in the app. Text link, no auto-open.
  **Built as:** the row renders whenever the strip is on the `active` screen and a slug
  resolves — not only on the Accept frame — so the link is still there when My Macros is
  reopened. New i18n key: `examplePlatesDisclaimer` (10 locales).
  **Open taste call (owner, on device):** tighten to Accept-only if it reads as clutter.

### C. Website — second collection

- Extend `plates-locale-content.mjs` / `plates-locale-more.mjs` with the new collection

## Collection roadmap — which profiles to build

Only profiles the product can actually route to are worth pages. Available canonical lab
codes today: `CREATININE`, `UREA`/`BUN`, `CHOLESTEROL_LDL`, `NON_HDL_CHOLESTEROL`,
`CHOLESTEROL`, `CHOLESTEROL_HDL`, `TRIGLYCERIDES`, `GLUCOSE`, `HBA1C`, `TSH`.
Lab-status scanners exist for kidney, lipid, glycemic only.

| Priority | Slug | Order it serves | Routing signal | Note |
|---|------|-----------------|----------------|------|
| shipped | `lipid-protocol` | Lipid-primary | lipid labs + rules | Live, 10 locales |
| **next** | `glycemic-protocol` | Glycemic-primary — pre-diabetes → T2D | `HBA1C` / `GLUCOSE` high + rules | Biggest overlap with our users; CGM makes the meal→response loop visible in-app |
| 2 | `weight-protocol` | Body-composition-primary — protein-forward, satiety | default `weight` primary | Covers the largest self-serve group, who today see nothing |
| 3 | `glp1-support` | Rapid loss on GLP-1 — lean-mass protection, small volumes, protein + fiber floors | **rules only** (no lab code) | Timely, and Withings muscle-mass trend is real supporting data |
| 4 | `renal-protocol` | Renal protein cap | `CREATININE` / `UREA` high | Clinician-gated — never route from labs alone; protein-controlled portions carry real risk |
| on demand | `low-carb-protocol` | Explicit low-carb / keto | `explicit_low_carb` only | Must stay explicit; never inferred (`ai-judgment-not-regex`) |

**Pre-diabetes vs diabetes — one collection in v1.** `scanGlycemicLabStatus` only knows
`flag === 'high'` from the lab's own reference range; it cannot separate pre-diabetes
(HbA1c 5.7–6.4%) from diabetes. Do **not** ship a pre-diabetes-specific page or copy that
implies banding until HbA1c banding exists. The clinician's rules already carry that
distinction, which is another reason routing belongs to rules.

Deferred, with the reason (do not "add anyway"):

- **DASH / hypertension** — professionally standard, but there is no sodium code and no
  blood pressure in the snapshot. No routing signal, so no page.
- **MASLD / fatty liver** — needs `ALT` / `AST` canonical codes first (lab catalog work).
- **Thyroid** — `TSH` parses, but iodine / selenium are be-45 **markers**, i.e. a
  constraint layered on any plate, not a diet profile of its own.
- **Mediterranean** — a pattern, not a lab-routed order, and it overlaps lipid. If it ever
  ships, it is the generic example on the plates index, never a routed slug.
