## Problem

Clinic will save live **macro bounds** (floor and/or ceiling per axis, HARD or FLEX) on the
same overlay as rules. The phone still meters a single point `daily_macro_target` (`116/80g`)
with no ≤ ≥, and auto-apply can overwrite a kidney protein cap. After be-45, the Food Log
must show what the clinic ordered, and Gemini must not break HARD bounds.

## Design rules

- Bounds are **structured** (`axis`, `direction`, `value`, `strength`). Never parse rules
  text for grams (`ai-judgment-not-regex`).
- **Logged food:** `net = C − Fi` always (code math). **Orders:** C and C−Fi are independent.
- HARD clinic bounds beat phone point targets on that axis. FLEX is a guide only (no ≤ ≥,
  auto-apply may move).
- **History honesty:** clinic ≤ ≥ meters apply on/after `macros.effectiveFrom`. A rebuild
  recovers **2 local days** back from `updatedAt` (21–22 stay metered after an Aug 23 rebuild),
  then **locks** (`effectiveFromRev: 2`) so later Updates never walk further back and **must
  not advance** that start. **20 Aug and older** keep leftover point-target meters
  (`real / target`, e.g. `1294 / 1690`, no ≤ ≥). Treatment markers on those days use the same
  slash, not ≤ ≥. Treatment markers: each Food Log day shows the marker **order that was
  in effect that day** (`markersForDay` — current + `markers_json.history`, latest
  `updatedAt` day ≤ dayKey). Saving a new marker set **archives** the previous list; it must
  not blank past days or erase prior targets. Meal estimates in storage are never rewritten for
  display. Earlier days before the first order show no clinic marker meters.
- Same overlay pull as rules/markers (`GET /v1/clinic/overlays`). Persistence parity:
  canonical key, backup + clinic export.

## What ships

### A. Pull + storage

- `ClinicOverlayService.pullClinicOverlaysFull` reads `overlay.macros` → store
  `healthings:clinicMacroBounds`
  `{ bounds: MacroBound[], updatedAt, source: 'clinic' }`.
- `macros` is a **sibling of `rules` and `markers`** on the same overlay pull — not grams appended to
  rules text (would mean parsing prose on the phone) and not treatment-marker rows (no floor+ceiling
  pair, no % anchor, no activity add-back). Three fields, one request, one refresh.
- New `ClinicMacroBoundsService.ts` (load/save/types + feasibility helpers shared conceptually
  with server: one floor + one ceiling per axis, floor < ceiling).
- Key on backup / ShareExport / cloud backup inclusion lists.
- Empty or null overlay macros → clear clinic bounds (do not invent defaults). The Food Log returns to
  `eaten / daily_macro_target` with no signs — the pre-be-45 display. This is also the server-rollback
  path, so it must be a clean, tested state, not an afterthought.
- **Skip unknown, keep the rest.** An unrecognised `axis`, `kind`, or `of` → drop that one bound, log,
  render everything else. If a `percent` bound arrives with no usable base, fall back to its
  `resolvedValue`. Never discard the whole payload and never crash the pull.
- Store bounds **as ordered**, including `kind`/`of`/`activityAddBack`/`followsActivity`. Do **not**
  flatten to grams on pull — the phone resolves per day (below). Server `resolvedValue` is the
  clinician's Confirm snapshot for the portal, not the meter.

### B. Food Log meters (`FoodMacroStrip` `MacroBar`)

For each of kcal, P, C, F, Fi, C−Fi:

| Clinic HARD on that axis | Right-hand text | Color |
|---|---|---|
| ceiling only | `today ≤ N` + unit | red if today > N (keep ~5% slack only if we already had it for caps; **do not** slack HARD clinic caps — owner: 113 allowed, 114 not) |
| floor only | `today ≥ N` | green if today ≥ N (same as Fi/H2O today) |
| both | `today  lo–hi` e.g. `102  90–113g` | in range = ok; below floor or above ceiling = red |
| none / FLEX only | keep `today/pointTarget` (current) | current rules |

### B2. Daily resolution — which meters move

Resolve every bound to grams/kcal **for the shown day** before rendering. Code math only, no AI.

| Bound | Resolves to | Moves during the day |
|---|---|---|
| `kind: constant` | `value` | no |
| `kind: percent`, `of: kcal_order` | `value/100 × kcalBase / (fat ? 9 : 4)` | no |
| `kind: percent`, `of: kcal_eaten` (markers: SatF) | same math on today's eaten kcal | **yes** — every meal |
| kcal ceiling with `activityAddBack` | see below | **yes** — upward only, capped |

**kcal add-back** (Michal/Stav: base 2000, threshold 400, cap 2300):

```
activityKcal = today's measured activity kcal — Activity Log sessions + watch/steps burn.
               NOT BMR, NOT total burn. Same number the energy row already uses.
extra        = max(0, activityKcal - thresholdKcal) * (ratio ?? 1)
ceiling      = min(value + extra, capValue)     // never below value, never above capValue
```

- Caption under the kcal bar when boosted: `2000 + 300 activity` (`appLocale`, numbers `ltr`).
- **No activity data** (watch off, no sync, no session) → `ceiling = value` + caption saying activity
  was not counted. Never infer a session, never infer from steps alone if the burn number is absent.
- `kcalBase` for `of: kcal_order` percent bounds is the **base** `value`, not the boosted ceiling,
  unless that bound has `followsActivity: true`. Stav's C stays `≤ 150 g` on a training day and goes
  red at 152 while kcal is green — intended, not a bug.
- Past days: resolve against **that day's** stored activity, not today's.

**No patient day-kind toggle in v1.** The phone measures the session; it does not ask.

### C. HARD wiring — every AI macro surface

**One engine (owner 2026-08-23):** phone Update and weigh-in/lab auto-apply call the
same clinic Propose as Rules Save (`POST /v1/account/macros/rebuild` → `proposeClinicMacroOrder`).
They write live bounds and **must not** call `reviseMacroTargetsWithGemini` / the 7-day P/C/F point
card. Empty My Rules → error (Update) or skip (weigh-in). No leftover point.

**Quick Start does not author a diet (owner 2026-08-23):** the targets step may AI-suggest a
**body** goal (weight / fat / muscle). It must not invent or save a `daily_macro_target` point.
If My Rules exist, same Propose rebuild; if not, macros stay empty until the user or clinic writes
rules and taps Update. Clinic decides, AI executes.

**Chat is not a command bar (owner 2026-08-23):** no `/macros`, `/recipe`, `/eat`, `/create` in
mentor chat. Those hijacks only caused trouble. Period review `/7` `/30` `/yesterday` stay.
Rebuild live macros from **My Macros → Update**. Recipe talk is prose in the nutritionist tab.

Pass clinic HARD bounds into:

- mentor chat context
- meal rule-check if it already receives markers

**Once clinic live macros exist for that day, leftover `daily_macro_target` is deleted**
(phone store + clinic snapshot on rules Save / macros write) **and must not appear in Gemini
prompts** (coach, chat USER DATA, PERIOD REVIEW, recipe/meal-plan, action-item fallbacks,
clinic mentor chat). Clinic HARD axes only (`Clinic live macros: C ≥ 65g | C−Fi ≤ 43g | …`).
Unordered axes are omitted from the prompt — do not fill them from the old phone point
(C 80, P 112, …). After Update, solo users have the same live bounds as clinic Save.

Verbatim block, e.g. `HARD from clinic: protein_g floor 90 g/day; protein_g ceiling 113 g/day; net_carb_g ceiling 43 g/day`. Judgment in the prompt; clamp/reject in **code** after Gemini returns a point so P/C/F/kcal cannot land outside HARD bands. Auto-apply must **not** write `daily_macro_target` while clinic HARD macros apply today.

Auto-apply must never emit a point that violates HARD (same as prompt110 markers). If conflict is unavoidable, keep the clinic bound and say so in reasoning.

FLEX bounds: include as “FLEX guide” in the prompt only; do not clamp.

Pass **resolved-for-today** numbers, and say what they resolved from, so Gemini does not re-derive
them: `HARD from clinic: kcal ceiling 2300 today (base 2000 + 300 measured activity); carb_g ceiling
150 g (30% of the 2000 target — does NOT rise on training days)`. Clamp in code against the same
resolved values.

### D. My Macros strip

Update requires **My Rules**, not a body scan. After Propose applies, skip the old P/C/F confirm
card (`onSaved(null)` + refresh meters). Patient must **not** edit HARD clinic axes (view-only
numbers + signs). Unordered / FLEX axes stay listed on Food Log with no leftover point.
