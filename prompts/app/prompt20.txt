## Prompt 20 — Photo assistant: analyze → chat → add/remove → approve

**Phase 1 (shipped):** photo session, add/remove preview, approve-before-apply, stacked preview on phone.
**Phase 2 (deferred):** dedupe on add, partial-gram remove, discard photo session, highlight matched lines.
**Phase 3 (new):** problem-only meal safety alert (blocking modal + red problem markers on offending lines).

### Vision
When logging or **editing** a meal, the user can attach photos (camera or gallery),
correct the AI item list via chat, then explicitly **add** those items to the meal
or **remove** matching items (photo shows what was **not** eaten / leftovers).

Nothing merges until the user sees **current vs updated** lists and taps **Approve**.

Replaces the old before/after dual-photo flow.

---

## User flow

```
1. 📷 Camera or gallery (idle new meal, or "Update with a photo" while editing)
2. 🤖 Gemini analyzes photo → item list (photo session only)
3. 💬 Chat corrections on the photo list (same JSON format as today)
4. User chooses intent:
     [ Add to meal ]     [ Remove from meal ]
   Empty meal: single button [ Use as meal ] (= add to empty)
   Remove = "this photo is food I did NOT eat" → drop matching lines from meal
5. Preview — stacked vertically (phone-friendly):
     CURRENT MEAL
     AFTER UPDATE
     + macro delta (Δ kcal, P/C/F)
6. [ Cancel ]  [ Approve update ]  → updates working meal, clears photo session
7. [ ✓ Save meal ]  → persists (unchanged)
```

User can repeat steps 1–6 (another photo) before saving.

---

## State model (FoodLogModal.tsx)

| State | Purpose |
|-------|---------|
| `items` | Approved working meal (what Save writes) |
| `mealHistory` | Gemini turns for **text corrections on the meal** (edit mode seed) |
| `photoSession` | Active photo analysis: `{ uri, base64, items, confidence, description, suggestion, history }` |
| `mergePreview` | `{ mode, before, after }` from local merge — no AI |

Rules:
- Photo chat **only** updates `photoSession.items`, never `items` directly.
- Meal chat (no active photo session) updates `items` via `analyzeFood` (existing text correction).
- Approve copies `mergePreview.after` → `items`.
- Save bar hidden while `mergePreview` is open — user must Approve or Cancel first.

---

## Chat input (single bar, context-aware)

One chat field on the result screen; placeholder and routing depend on context:

| Context | Placeholder / behaviour |
|---------|-------------------------|
| `photoSession` active | Correct **photo list** only ("only half the pita"…) |
| No photo session | Correct **meal** via text ("add a coffee"…) |

Meal text correction is blocked while a photo session is active (finish or approve photo flow first).

---

## Local merge (mealPhotoMerge.ts)

No Gemini call for add/remove.

| Mode | Logic |
|------|--------|
| **add** | Concatenate photo items onto meal (no dedupe in Phase 1) |
| **remove** | Drop meal rows whose name matches any photo item (fuzzy: name / name_local, substring) |

User must fix photo list via chat before Remove if portions differ (whole-line remove only).

UI hint shown: *Remove = photo shows food you did not eat (leftovers)*.

---

## UI sections (result screen)

1. **Your meal** — `items` list + total (visible when non-empty or editing)
2. **Photo assistant** (when `photoSession`):
   - Thumbnail, confidence, description
   - Photo item list ("From photo")
   - 📷 / 🖼 New photo replaces session (fresh history)
   - Add to meal | Remove from meal (or **Use as meal** if empty)
3. **Preview** (when `mergePreview`):
   - **Current meal** on top, **After update** below (stacked, not side-by-side)
   - Δ macros row
   - Cancel | Approve update
4. **Chat** — single input (see above); hidden during preview
5. **Update with a photo** — camera/gallery when meal has items and no active photo session
6. Date/time, Save, Delete

## Phase 3 (priority) — Problem-only alert on meal mismatch

User requirement (2026-06-17): if a photo-based meal (or edited meal) conflicts with targets/rules,
show an **unmissable** alert. If no mismatch, **show nothing**.

### Trigger
- Run check on **Save meal** (after latest photo/text edits are applied to `items`).
- If no issues: save immediately (silent).
- If issues exist: block with modal and mark problematic lines in red.

### Detection scope (v1)
1. **Macro target mismatch** (today totals including this meal):
   - carbs over target
   - calories over target
   - protein far under expected pace (optional warning severity)
2. **My Rules mismatch** from `userRules.constraints`:
   - direct keyword-level conflicts only in v1 (clear violations)

No mismatch => no alert, no coach/chat interruption.

### UX behavior
- Blocking modal (cannot miss):
  - Title: "Nutritionist alert"
  - Body: short problem message (1-3 lines max)
  - Buttons: `Edit meal` (primary), `Save anyway` (secondary)
- Meal item rows that triggered checks get:
  - red border (or red left rail)
  - small warning icon/dot
- Keep warning state tied to current `items`; clear markers when issue is fixed.

### Data model additions (FoodLogModal)
- `mealIssues: MealIssue[]`
- `showIssueModal: boolean`
- `overrideSaveOnce: boolean` (set true only after user taps `Save anyway` for current snapshot)

Suggested shape:
```ts
type MealIssue = {
  id: string;
  severity: 'warning' | 'critical';
  code: 'carb_over' | 'kcal_over' | 'protein_low' | 'rule_conflict';
  message: string;
  itemNames?: string[]; // lines to mark red
};
```

### Files
- `app/src/components/FoodLogModal.tsx` — issue detection, modal gate, red row styling
- `app/src/services/TargetService.ts` (read-only use) — macro target / user rules fetch for check
- optional helper:
  - `app/src/logic/mealIssueAnalysis.ts` — pure local mismatch detector

### Acceptance checklist (Phase 3)
- [ ] Save meal with no mismatch => no modal, no red markers.
- [ ] Save meal with mismatch => modal appears before save.
- [ ] `Edit meal` keeps modal closed and leaves unsaved meal open with red-marked offending lines.
- [ ] `Save anyway` persists once for current snapshot.
- [ ] After fixing offending items, red markers disappear and save is silent.
